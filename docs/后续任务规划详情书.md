## 1. 长期目标与能力差距

### 1.1 用户长期目标（原意归纳，按优先级）

1. **判断信息质量**：准确性、出处、时效性；默认"接触到的内容存疑"，靠后续查证与长周期观察修正。
2. **降低信息不对称**：少消费同质化/搬运内容，多看一手与高质量来源。
3. **每日推荐与日报**：自动采集 + 推荐 + 生成每日报告（当前是"单次命令"，不是"已部署的定时任务"）。
4. **导入与查询**：导入自己关注的内容，之后能查、能复盘、能追问"这条从哪来、后来怎样了"。
5. **寻因导果**：由果溯因（这条信息的上游在哪）、由因推果（若为真，应该能看到什么）。
6. **关系网络**：把异构信息组织成实体/主张/事件的关系网，辅助发现关联。
7. **现实检验闭环**：规则/先验产生可证伪预测 → 世界产生裁决 → 裁决回流修正（当前只到"人工结算 + Brier"，不自动学习）。
8. **历史表示法的启发**：古籍/哲学/术数体系只作为假设结构与表示法参考，**绝不作为因果证据**。

### 1.2 能力差距矩阵

| 能力 | 现状（2026-11-11） | 差距 | 对应阶段 |
|---|---|---|---|
| 内容导入 | 手工 JSON 离线导入；`import` 支持文本/文件/URL 但走 LLM 且需 `--allow-remote` | 真实 LLM 抽取未验收（外部额度）；无法从订阅条目一键转入 | P1-1 |
| 查询/检索 | `claims --domain/--min`、`due`、`sources`、`inbox`、`item` | 无关键词全文检索、无按来源/日期/层级过滤、无文档列表/详情 | P1-2 |
| 出处链 | reporter→origin 两级 + quote；独立根计数；跨源同文提示（启发式） | 多级转述链、来源别名/上游关系仍缺 | P2-1（后续） |
| 内容甄别 | 来源类型先验 + 实验分 + 待核验线索；跨源重复提示 | 无排序质量评估、无跨源独立性的系统判定 | P2-2/P2-3 |
| 每日推荐 | 单次 `collect`/`daily`，本地文本输出 + `digests` 历史 | 无调度、无投递、无未读提醒 | P3 |
| 日报 | 手动/单次生成，文本报告 | 无定时、无外部投递、无多日对比/趋势 | P3/P4 |
| 预测与结算 | 登记、冻结 p、人工结算、Brier、到期列表 | 无到期提醒推送、无证据附件、无校准评估 | P4 |
| 反馈闭环 | 结算只记录结果，不回写来源/主张 | 无校准评估；来源先验不随结果更新（有意为之） | P4（谨慎） |
| 关系网络 | 无 | 无实体/关系/时间线/图导出 | P5 |
| 因果辅助 | 无 | 只有预测与人工结算；无假设登记/反证跟踪 | P5 |
| Web UI / 分发 | 无，仅 CLI；无打包 | 无 UI、无安装包、无迁移 | P6（可选） |

## 2. 指导原则与授权边界

### 2.1 工程原则

1. **离线优先**：核心能力（导入 JSON、查询、日报、测试）不依赖网络与模型；联网功能必须可关闭、可诊断。
2. **标准库优先**：运行时只依赖 Python 标准库；新增第三方依赖须有充分理由并经用户同意。
3. **可测试**：任何新行为先写失败测试（红）再实现（绿）；测试不访问真实网络、不调用真实模型（用假 DNS/socket、mock、临时文件）。
4. **留痕**：评分、结算、采集、投递都要有可追溯记录；错误要落 `last_error`/日志类字段，而不是静默。
5. **失败可诊断**：错误信息不泄露密钥/正文；网络/额度错误给出固定、可操作的本地提示。
6. **不伪造**：示例一律虚构；不内置"猜的真实订阅源"；没有的数据不编（时间、来源、URL 一律可为空并显式标注）。
7. **原子性**：涉及多表写入的操作要么全成要么全滚（`db.atomic`）。
8. **小步交付**：一次只做一个 WP，验收通过再下一个。

### 2.2 认识论原则（不可为了"好用"而破坏）

1. 实验分**不是**真伪概率；任何展示都要保留"未校准"声明。
2. `hard_signal` 只是待核验线索，**永不**加分。
3. 出处链存在**不证明**证据独立；不同来源可能共享同一上游。
4. 预测 `p` 只能人工登记、登记即冻结；模型不得生成 `p`。
5. 预测命中/失败**不改变**来源先验与主张分数（当前实现即如此，不要"优化"成自动回写）。
6. Brier 只评价已登记概率的预测，不替代事实核查，不证明因果。
7. 日报/推荐是"未核验线索"，不是"已核实结论"。
8. 古法/术数/哲学只能产出假设与表示法，不能产出因果结论。

### 2.3 授权边界

| 类型 | 行为 | 需要什么 |
|---|---|---|
| **绝对禁止** | 自动改计费/额度/密钥；自动把内容发给外部模型或第三方；伪造来源/数据；把实验分当概率对外宣称；绕过付费墙/robots/访问控制；修改 `D:\ai奇门` 或把它整合进来 | 无（任何情况下都不做） |
| **需用户明确授权** | 安装系统定时任务/计划任务；向邮件/IM/Webhook 投递日报；新增第三方依赖；提交/推送 git；修改默认订阅源清单；联网抓取用户未提供的私有源 | 用户明确说"可以/安装/发送" |
| **默认可做（本地、离线、可回滚）** | 新增本地命令、SQLite 表、测试、文档修订、虚构演示、只读验证、本地日报文件生成 | 遵守本规划与验收标准 |
| **需先询问** | 删除已有样例/演练库；改变现有 CLI 语义；改变评分/结算规则；引入 DB 迁移 | 用户确认 |

| 阶段 | 主题 | 优先级 | 依赖 | 规模（估） | 主要风险 |

### P1 导入与查询能力（最高优先）

#### P1-1 `[已完成]` 订阅条目 → 文档/主张 桥接（`ingest`）
- 目标：让"待读队列里看中的条目"能一键进入账簿流程，而不是手动复制链接再 `import --url`。
- 输入：`feed_items.id`（说明：条目本身只是未核验摘要；抓取全文仍需安全校验）。
- 输出：`documents` 一条（记录 `url`、`reporter_source_id`=订阅来源或"未知来源"、`raw`）；可选：抽取后生成 `claims/chains`。
- 设计要点：
  - 默认**只建文档、不抽取**（离线、零费用）；加 `--extract` + `--allow-remote` 才调用模型。
  - 抽取源优先级：条目 `summary`（短）/ 原文 URL 抓取全文；两者都要显式提示"内容未核验"。
  - 已转换过的条目要能识别（避免重复 `documents`）；建议新增 `documents.source_item_id` 或 `feed_items.document_id`（列级变更需考虑旧库，见 P1-2 的迁移说明）。
  - 不改变 `feed_items.read_at` 语义（转换≠已核实）。
- 涉及文件：`causal_ledger/feeds.py` 或新 `ingest.py`、`causal_ledger/cli.py`、`docs/design.md`、测试。
- 验收：
  - 离线：条目 → 文档，`documents` +1，`claims` 不变（未 `--extract` 时）；重复调用不重复建文档或明确报错。
  - 开启抽取时：mock LLM 路径下生成 claims；模型 `p` 被剥离。
  - 无 `--allow-remote` 时拒绝且不建库/不写库。
  - 现有用例全绿 + 新增用例。
- **本次交付（2026-11-11）**：`causal_ledger/ingest.py`；`db.py` 加性表 `feed_ingests(feed_item_id UNIQUE, document_id)` 保证幂等；CLI `ingest ID [--fetch] [--extract --allow-remote] [--claim TEXT] [--claim-key/--domain/--layer/--hard-signal/--quote/--origin/--origin-type]`；`import-json FILE --feed-item ID` 支持多主张离线关联；`item` 显示已转换文档；`tests/test_ingest.py` 13 + `tests/test_manual_claim.py` 6 个用例；全量 **270 passed + 119 subtests**。人工接账是**离线**补链路径，不依赖 LLM 额度。

### P2 内容甄别与推荐质量

#### P2-1 `[待开始]` 来源注册表管理
- 目标：能维护来源别名与类型，减少"同名不同源/同源不同名"导致的独立根误计。
- 命令草案：`source add NAME --type T`、`source list`、`source alias OLD NEW`、`source type NAME TYPE`。
- 设计要点：别名只影响后续链的 origin 归并；**历史数据迁移必须显式确认**；类型修正沿用现有"unknown→已知类型触发重算"逻辑（`provenance.ensure_source`）。
- 验收：新增来源/别名/类型修正的离线测试；重算已有主张的边界；不改变"独立根计数只是计数"的语义。

#### P2-2 `[已完成]` 跨源重复/转载识别（只提示，不合并）
- 目标：不同订阅转载同一文章时，在 `inbox`/`daily` 中提示"疑似重复"，减少信息噪声。
- 设计要点：URL 归一化（去跟踪参数/协议/末尾斜杠/默认端口）+ 标题指纹相似度（去标点/空白、Unicode casefold）；**只提示**，不自动合并、不自动去重到只剩一条。
- 验收：固定样本集上误报/漏报可评估；输出显式"疑似重复（仅提示，未验证）"；结果键集合不变、不改分。
- **本次交付（2026-11-11）**：`causal_ledger/dedup.py`（`normalize_url`/`title_fingerprint`/`titles_similar`/`annotate_duplicates`）；`feeds.recommend` 在推荐依据末尾追加提示；`tests/test_dedup.py` 5 个用例。真实推送中未触发（所选 10 条无跨源同文），合成样例已验证。

#### P2-3 `[待开始]` 推荐质量与候选窗口
- 目标：在"只看最新 5000 条候选"的硬限制下，让推荐更可控、可解释。
- 设计要点：可选 `--offset` 或按主题分页；watchlist（主题词表，存库）；推荐理由已含时间/主题/每源上限/候选窗口披露；增加"为什么没推荐"的可选调试输出（`--explain-empty`）。
- 验收：边界测试（5000 之外不推荐且明确说明）；主题词命中与大小写；不改变"未核验"语义。

#### P2-4 `[待开始]` 采集健壮性
- 目标：减少重复抓取与瞬时失败。
- 设计要点：条件请求（`If-None-Match`/`If-Modified-Since`，304 不算失败）；可配置超时；对 5xx/超时做有限重试（次数/退避上限，默认关闭或最多 1 次）；错误分类（网络/HTTP/解析/数据库）分开记录；仍不写原始 XML 到 `last_error`。
- 验收：假 socket/HTTP 桩测试 304、5xx、超时、解析失败；无真实网络。

#### P2-5 `[待开始]` 时间语义完善
- 目标：明确"源称发布时间/采集时间/结算时间"的边界，避免未来时间与窗口错位。
- 设计要点：`published_at` 解析的时区规则已有（无时区→`NULL`）；补充"未来发布时间"处理与提示；日报窗口本机日→UTC 规则保持；考虑新增 `published_confidence`（不必要则 YAGNI）。
- 验收：固定时间测试（跨时区、未来、无时区、非法）；不改变已有语义。

### P3 每日推荐与投递

#### P3-1 `[已完成]` 日报历史与投递记录
- 目标：每次 `daily` 的结果可归档、可追溯（此前只支持写一个新文件）。
- 已实现：`digests(id, created_at, kind, path, ok, summary_json)` 加性表；`daily` 每次生成后写入一条（含逐源采集结果、参数、ok）；`digests --limit N` 只读列出；`daily --brief` 提供紧凑文本简报 v3；`daily --html` 单文件两层 HTML；`daily --html-dir DIR [--fetch-details]` 多页简报站；**本地单应用 `serve`**（阅读/往期/末尾备注，默认仅本机，局域网需 token）；**个体因果基线 MVP**：`profile import/show/clear` + `daily --mode` + 通线/轻个体线/个体线降级 + "与你有关/你在哪一段"（启发式）；**保险箱**（DPAPI + 解锁审计）；**7 天校准**（`calibrate`）；**盲评与消融**（`eval`）；**零月费云发布**（`cloud` + GitHub Actions/Pages + Server酱）；**周报与保留策略**（`cloud --weekly-only`）。
- 仍未实现：`deliveries`（外部投递记录）属于 P3-3，需用户明确授权。
- 验收：生成/重复生成/部分失败三类测试；不覆盖已有文件；可列出历史。

#### P3-2 `[需授权]` 调度方案（不默认安装）
- 目标：如果用户要"每日自动"，提供**可选**的本地调度方案。
- 建议：Windows 计划任务（`schtasks`）脚本模板 + `daily --no-fetch` 安全模式 + 日志路径 + 卸载说明；默认**不安装**、不常驻守护进程。
- 授权：安装/卸载必须用户明确要求；脚本本身可先交付但不执行。
- 验收：手动执行脚本可生成日报；任务安装/卸载有文档；不引入后台服务。

#### P3-3 `[需授权]` 外部投递（邮件/IM/Webhook）
- 目标：把日报送到用户指定渠道（可选）。
- 设计要点：显式 `deliver` 子命令 + 渠道配置（本地文件/邮件 SMTP/IM Webhook）；内容脱敏（不默认附带 raw 正文/密钥）；失败重试有上限；默认关闭。
- 授权：需要用户提供渠道与明确同意；不自动外发。
- 验收：本地 fake SMTP/HTTP 桩测试；失败可见；不泄露凭据。

#### P3-4 `[待开始]` 未读提醒与已读同步
- 目标：`daily`/`inbox` 顶部汇总未读数与最旧未读年龄；`read` 支持批量。
- 验收：计数准确；已读幂等；无网络。

### P4 结算与反馈闭环

#### P4-1 `[待开始]` 到期提醒与结算引导
- 目标：日报/`due` 更醒目地提醒到期项，附核验方法；不自动结算。
- 验收：到期/今日/逾期分类测试；无自动状态变更。

#### P4-2 `[待开始]` 结算证据记录增强
- 目标：`settle --note` 之外可记录证据位置（URL/文件/截图路径）与核验时间（结构化字段）。
- 设计要点：新增 `predictions.evidence_ref`/`verified_at` 等列需迁移方案（见 P6-2）；或先存 JSON 备注，避免过早改表。
- 验收：迁移兼容旧库；不改变"人工记录≠系统核实"语义。

#### P4-3 `[待开始]` 校准评估（只统计，不改先验）
- 目标：按来源类型/领域/时间分组统计预测的 Brier 与命中率，明确样本量与置信区间，提示"样本太小不宜校准"。
- 设计要点：只做**描述性统计**；不自动修改 `source_domain_stats.alpha/beta`；报告显式"不是来源真实可靠率"。
- 验收：固定样本测试；小样本提示；不写回先验。

#### P4-4 `[需授权]` 受控的来源先验更新（谨慎，默认不做）
- 目标：在足够结算样本 + 用户批准后，允许**显式命令**（非自动）更新某来源×领域先验，并留痕可回滚。
- 前置：P4-3 完成；已定义最小样本阈值（如 ≥30 次独立结算）与回滚机制。
- 红线：不自动学习；不把预测命中当因果证据；不把来源"命中率"当真实可靠率对外宣称。
- 验收：回滚测试；留痕完整；默认关闭。

### P5 关系网与因果辅助（研究性）

#### P5-1 `[待开始]` 主张/实体图导出
- 目标：把 `claims/chains/sources` 导出为本地只读图（Graphviz DOT / JSON），供人工查看"哪些主张共享来源、哪些互相引用"。
- 验收：固定样例 DOT 可生成；不联网；节点/边语义标注"未验证"。

#### P5-2 `[待开始]` 主张关联
- 目标：识别同主体/同主题的主张簇（`canonical_key` 主体段相同、共现来源、同文档），辅助"寻因导果"。
- 设计要点：只做**关联提示**；不推断因果方向；可选 `relations` 表存显式人工关系。
- 验收：固定样本；无误合并；输出带"假设"标注。

#### P5-3 `[待开始]` 假设登记表
- 目标：把"因为 A 所以 B""A 可能解释 B"作为**假设**登记（含证据 for/against、可证伪预测、状态），与已核验主张分离。
- 建议表：`hypotheses(id, text, created_at, status, note)`、`hypothesis_claims(hypothesis_id, claim_id, role in {cause,effect,evidence_for,evidence_against})`。
- 验收：登记/查询/关联/状态流转测试；报告中显式"假设，未验证"。

#### P5-4 `[待开始]` 时间线视图
- 目标：按时间排列文档/主张/预测/结算，辅助看"信息出现→预测→裁决"的顺序。
- 验收：本地文本时间线；时区正确；无网络。

#### P5-5 `[长期研究]` 因果识别
- 目标：明确边界——本项目可以登记因果**假设**与检验设计（自然实验、前后对比），**不输出**因果结论。
- 前置：P5-3；统计/因果推断方法论评审；用户明确立项。

### P6 Web UI / 分发（可选）

#### P6-1 `[需授权]` 本地只读 Web 视图
- 目标：浏览器查看账簿/待读/日报（只读，不做写操作）。
- 建议：标准库 `http.server` + 静态导出（不引入 Flask/Django）；默认仅 `127.0.0.1`；需用户明确要求。
- 验收：本地启动/关闭；只读；不暴露到公网；安全测试（路径穿越/模板注入）。

- 验收：旧库升级测试；`pip install -e` 后命令可用；不改变运行时无第三方依赖。

## 5. 里程碑与完成定义（DoD）

每个 WP 完成的统一标准：

1. **功能**：按 WP 描述可用，CLI 输出符合预期。
2. **测试**：新增行为有测试；`python -m pytest tests -q` 全绿（当前基线 325 + 119 subtests，后续只增不减）。
3. **离线**：核心测试不访问真实网络/模型；涉及网络的新代码用假 socket/HTTP 桩。
4. **边界**：保留 §2.2 全部声明；新输出带"未核验/未校准"等必要提示。
5. **文档**：`docs/design.md` 与新增命令同步；若语义变化，`docs/接手报告.md` 追加变更记录。
6. **无伪造**：示例/测试数据全部虚构并标注。
7. **无越权**：不安装定时任务、不自动外发、不改计费/密钥、不 git 提交（除非用户要求）。
